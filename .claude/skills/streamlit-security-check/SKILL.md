# Streamlit / Python アプリのセキュリティチェック

目的は、**そのアプリの使われ方に合った、本当に対処すべき問題** を見つけて分かりやすく伝え、ユーザーが選んだものを安全に直すこと。
一般論の長いリストより、「このコードのこの行が、こういう状況でこう悪用される」という具体性の方が役に立つ。
利用者はプログラミング学習中のこともあるので、専門用語には一言説明を添える。

## 手順

### 1. 前提をつかむ（数分で済ませる）

- `CLAUDE.md` / `README` / デプロイ設定を読み、**公開範囲**（ローカルのみ / LAN / インターネット公開）と **プロジェクトの方針**（例: 「個人用なので認証は不要」）を把握する。
- 方針として決められていることは尊重する。例えば認証不要の方針なら「認証がない」を高リスクとして押し付けず、「公開するならここが危険になる」という条件付きの注意として書く。
- 公開範囲が分からなければ、ユーザーに聞いて止まるのではなく「ローカル利用を前提に判断、公開時の注意は別に記載」と仮定を明示して進める。

### 2. 機械的なスキャン

```bash
python <このスキルのパス>/scripts/scan.py "<プロジェクトのパス>"
```

秘密情報らしき文字列、`.gitignore` の漏れ、git 履歴、危険な関数、Streamlit 設定、依存関係を下見する。**パターン一致なので誤検知も見逃しもある**。結果は出発点として使い、次の手順で必ず裏を取る。

### 3. コードを読む（ここが本番）

すべてのソースを読み、**データの流れ** を追う:
- 外部から入るもの（フォーム入力、アップロード、URL、LLM の出力、環境変数）は、最終的にどこへ行くか（画面表示、プロンプト、ファイル、コマンド、外部通信）。
- 秘密情報はどこから読まれ、どこへ渡り、画面・ログ・エラーに出る経路がないか。

観点ごとの詳しい確認方法と直し方は `references/checklist.md` にある。全11章のうち、アプリに関係する章を読んで当てはめる（LLM を使っていれば4章、ファイルアップロードがあれば6章、など）。

依存ライブラリは `pip show <名前>` で実際のバージョンを確認する。`pip-audit` が使えれば実行する。無ければ導入するかどうかをユーザーに聞く（勝手にインストールしない）。

### 4. 仕分けと重要度

スキャン結果の誤検知は除き、問題ごとに重要度をつける。**公開範囲で重要度は変わる**。

| 重要度 | 目安 |
|---|---|
| 🔴 高 | 今の使い方のままで実害が出うる。秘密情報の直書き・コミット、外部入力の eval/shell/SQL、LLM 出力の実行、公開アプリでのサーバー側キーの流用 |
| 🟠 中 | 条件がそろうと実害。LLM 出力やユーザー入力の unsafe HTML 表示、TLS 検証オフ、XSRF 無効化、アップロードのパス操作 |
| 🟡 低 | 影響が限定的・多層防御。エラー詳細の表示（ローカル個人用）、入力サイズ上限なし、バージョン未固定 |
| ℹ️ 情報 | 問題ではないが知っておくべきこと。公開時の注意、良くできている点 |

**良くできている点も書く**。何が安全なのかを知ると、今後の変更で壊さずに済む。

### 5. レポート

次の形式で、チャットに日本語で出力する（ファイル保存を頼まれたら同じ内容を `security-report.md` などに保存）:

```markdown
# セキュリティチェック結果: <アプリ名>

## 概要
- 前提: <公開範囲・方針。仮定した場合はそう書く>
- 結果: 🔴高 N件 / 🟠中 N件 / 🟡低 N件 / ℹ️情報 N件
- ひとことで: <一番伝えたいこと 1〜2文>

## 指摘事項
### [🔴高-1] <タイトル>
- 場所: `app.py:67`
- 内容: <何が問題か。専門用語には一言説明>
- 起こりうること: <具体的な悪用・事故のシナリオ>
- 修正案: <方針。短いコード例があれば>

（重要度の高い順に続ける）

## 良くできている点
- ...

## 公開する場合の追加の注意（ローカル専用のときのみ）
- ...

## 確認できなかったこと
- <例: git 管理外のため履歴は未確認 / pip-audit 未実行>
```

**秘密情報の値は、レポートでもどこでも絶対に表示しない**。「`.env` に `GEMINI_API_KEY` がある」「`config.py:3` に Google API キーらしき文字列（`AIza****`）」までに留める。`.env` の中身を `cat` で表示する必要もない（キー名だけ知りたければ `=` より左だけを取り出す）。

### 6. どれを直すか確認する

レポートの最後に、修正する候補を番号付きで示し、どれを直すかユーザーに聞く（例: 「高-1 と中-1 を直しますか？ まとめて全部も可能です」）。
- ユーザーが最初から「直して」と頼んでいた場合は、**低リスクで小さい修正** はそのまま進めてよい。ただし次のものは必ず先に確認する: ファイル構成の変更、ライブラリの追加、既存機能の削除・挙動の変更（例: サーバー側キーのフォールバックをやめる）。これらはユーザーの使い方を変えてしまうため。
- 質問できない状況（自動実行など）なら、確認が必要な修正は行わず、レポートに「確認後に実施する修正」として残す。

### 7. 修正と検証

- 既存のコードの書き方（命名、コメントの量、言語）に合わせ、**問題を直すのに必要な最小限の変更** にする。ついでのリファクタリングはしない。
- プロジェクトのルール（CLAUDE.md の「ライブラリを追加したら requirements.txt も更新」など）に従う。
- 直したら構文チェック（`python -m py_compile <変更したファイル>`）を行い、スキャンを再実行して指摘が消えたか確認する。
- Streamlit は起動中に `app.py` 以外のモジュールの変更を反映しないことがあるので、再起動（`Ctrl + C` → `streamlit run app.py`）を案内する。
- **秘密情報が漏れていた場合**、ファイルから消すだけでは不十分。発行元（例: Google AI Studio）でキーを無効化・再発行するよう、ユーザーに明確に伝える。これはユーザーにしかできない作業。

最後に「何を・なぜ直したか」を、指摘番号と対応づけて簡潔にまとめる。直さなかった指摘は残っていることも書く。
