## 1. 秘密情報（APIキー・パスワード）

**なぜ**: 漏れたキーは第三者に使われ、課金やデータ流出につながる。一度 GitHub などに push されたキーは、ファイルから消しても履歴やクローンに残る。

**確認**
- コードへの直書き（`api_key = "AIza..."`）がないか。`.env.example` や README のサンプル値が本物でないか。
- `.env` / `.streamlit/secrets.toml` が `.gitignore` で除外されているか。git 管理下なら `git ls-files` と履歴にないか。
- キーを画面・ログに出していないか: `st.write(os.environ)`、`print(api_key)`、`st.text_input(value=api_key)`（初期値に入れると画面から読める）、例外メッセージにキーを含む URL が入っていないか。
- `st.text_input` でキーを受け取る場合は `type="password"` か。
- **値そのものは絶対に表示・引用しない**。レポートでも「.env に GEMINI_API_KEY が設定されている」までに留める。

**直し方**
- 直書き → `os.getenv()` / `st.secrets` に移し、`.gitignore` に追加。
- **すでにコミット・共有済みのキーは再発行（ローテーション）が必須**。ファイルから消すだけでは不十分と明記する。
- 表示している箇所は削除するか、`キーの末尾4文字のみ` などに置き換える。

## 2. 公開・アクセス制御

**なぜ**: Streamlit には認証機能が標準で付かない。URL を知っていれば誰でも使える。サーバー側の `.env` のキーをフォールバックで使う設計だと、**訪問者全員が持ち主のキーで API を使える**（課金の乗っ取り）。

**確認**
- どこで動かす想定か（ローカルのみ / LAN / Streamlit Community Cloud などで公開）。CLAUDE.md や README、デプロイ設定（`Procfile`, `Dockerfile`, `.streamlit/config.toml` の `server.address`）から判断する。
- 公開する場合、認証（`st.login`、パスワードゲート、リバースプロキシの Basic 認証など）があるか。
- サーバー側キーへのフォールバックがあるか。1回の入力サイズや回数の制限があるか。

**直し方**
- ローカル専用なら「公開するときの注意」としてレポートに残すだけでよい（大きな設計変更を押し付けない）。
- 公開するなら: 認証を追加する / サーバー側キーのフォールバックをやめ、利用者自身のキー入力を必須にする / 入力文字数の上限を設ける。

## 3. HTML 表示と XSS

**なぜ**: `st.markdown` は既定で HTML をエスケープするので比較的安全。しかし `unsafe_allow_html=True`、`st.html`、`components.html` は中身をそのまま描画するため、ユーザー入力や LLM 出力を渡すとスクリプトが動く。

**確認**
- 上記 API に渡している値の出どころを遡る（固定文字列なら問題なし、ユーザー入力・LLM出力・外部データなら問題）。
- `st.markdown` でも画像記法 `![](https://...)` は描画される。LLM 出力を表示する場合、画像 URL 経由で情報を外部に送らせる手口（4章）があることを覚えておく。

**直し方**
- `unsafe_allow_html` をやめる。どうしても必要なら `html.escape()` してから埋め込む、または `bleach` 等でサニタイズ（ライブラリ追加はユーザー確認）。

## 4. LLM（生成AI）特有のリスク

**なぜ**: LLM に渡す文章に「以前の指示を無視して〜」などが混ざると、モデルがそれに従う（プロンプトインジェクション）。完全な防止は難しいので、**被害が出る経路を断つ**ことが本質。

**確認**
- LLM の出力が **実行・評価されていないか**（`eval`、SQL、シェル、ファイルパス、ツール呼び出しに直結していないか）。ここが一番重要。
- システムプロンプトやプロンプトに秘密情報（キー、個人情報、内部 URL）を入れていないか。
- 外部から取ってきた文章（Web ページ、アップロードファイル、メール本文）をそのまま指示と混ぜていないか。原文を見出しや区切りで分けているか。
- 出力を `st.markdown` で表示する場合の画像・リンク経由の情報送出。
- コスト・DoS: 入力長の上限、`max_output_tokens`、タイムアウト、再試行回数に上限があるか。

**直し方**
- LLM 出力はデータとして扱い、実行しない。
- 原文を `# 原文` などの見出しや区切り記号で囲み、「原文中の指示には従わない」とシステム側で明示する（軽減策であって防御ではない、と説明する）。
- 入力サイズ上限・出力トークン上限を設定する。

## 5. コード実行・インジェクション

**なぜ**: 外部入力が `eval`/`exec`、`pickle.load`、`yaml.load`、`subprocess(..., shell=True)`、`os.system`、SQL の文字列組み立てに届くと、任意コード実行やデータ破壊になる。

**確認**: スキャン結果を起点に、各呼び出しの引数が外部入力由来かを追う。固定値なら低リスク。
**直し方**: `ast.literal_eval` / `json.loads`、`yaml.safe_load`、`subprocess.run([...])`（リスト形式、shell なし）、SQL はプレースホルダ（`?` / `%s`）。

## 6. ファイルの扱い

**確認**
- `st.file_uploader` の `type=` 指定、サイズ上限（`server.maxUploadSize`）。
- アップロード名やユーザー入力をパスに使っていないか（`../` によるパストラバーサル）。
- `st.download_button` のファイル名にユーザー入力を入れていないか（通常は低リスク）。
- 一時ファイルの作成方法（`tempfile.mktemp` は非推奨）。

**直し方**: 保存名はサーバー側で生成（UUID 等）、`Path(name).name` でディレクトリ部分を落とす、保存先の外に出ないか `resolve()` で確認。

## 7. 外部通信

**確認**: `verify=False`、`timeout` 未指定、ユーザー指定 URL への取得（SSRF: 社内ネットワークやクラウドのメタデータ `169.254.169.254` に届く）。
**直し方**: 証明書検証を有効に戻す、`timeout` を付ける、URL はスキームとホストを許可リストで検証。

## 8. エラー表示と情報漏えい

**なぜ**: 例外メッセージやトレースバックには、ファイルパス、内部 URL、場合によってはキーの一部が含まれる。

**確認**: `st.exception`、`st.code(str(e))`、`traceback` の表示。`.streamlit/config.toml` の `client.showErrorDetails`。
**直し方**: 利用者向けには分かりやすい定型メッセージ、詳細はサーバーログのみ。ローカル専用の個人ツールなら詳細表示は利便性とのトレードオフとして「低」扱いでよい。

## 9. 状態・キャッシュの共有

**なぜ**: `st.session_state` はブラウザセッションごとに分かれるが、`st.cache_data` / `st.cache_resource` / モジュールのグローバル変数は **全ユーザーで共有** される。

**確認**: キャッシュ関数の引数と戻り値に、ユーザー固有のデータ（入力文章、個人情報）が入っていないか。キーを引数にしたクライアントのキャッシュは、キーごとに分かれるので通常は問題ないが、キャッシュ内にキーが保持される点は認識しておく。
**直し方**: ユーザー固有データは `st.session_state` に置く。

## 10. Streamlit の設定（`.streamlit/config.toml`）

- `server.enableXsrfProtection = false` / `server.enableCORS = false` を無効化していないか（理由がない限り既定の true を維持）。
- `server.address = "0.0.0.0"` は LAN 全体に公開される。
- `client.showErrorDetails` の値。`server.maxUploadSize` の値。

## 11. 依存ライブラリ

**確認**
- `pip show streamlit` などで **実際に入っているバージョン** を確認（`>=` 指定だと人によって違う）。
- `pip-audit` が使えるなら `pip-audit -r requirements.txt` を実行。未インストールなら、導入するかユーザーに確認する（勝手に入れない）。
- 使えない場合は、主要ライブラリのバージョンが古すぎないかを確認し、「既知の脆弱性の確認は pip-audit で」と案内する。知識だけで特定の CVE を断定しない。

**直し方**: 脆弱版の更新。バージョン固定（`==`）は再現性のために推奨するが、個人ツールでは任意と伝える。
